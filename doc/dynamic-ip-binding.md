# 动态出口：「账号 ↔ IP」绑定（2026-10-16 定稿）

> 需求方口径（用户）：**一个 IP = 5 个平台 × N 个账号**；记录 IP↔平台↔账号关系，用**本地一个文件**记录，
> 不落数据库；不管静态 IP；取 IP 仍一枚一枚取；「到期即解散，账号需要时才绑」——不做整体迁移。

## 1. 模型与参数

| 参数 | 配置项 | 默认 | 说明 |
|---|---|---|---|
| N（每枚 IP 的同平台账号数上限） | `GEO_DPS_ACCOUNTS_PER_IP` | 2 | 一个 IP = 5 平台 × N 个账号位。**越小越分散（风控更安全）、越费 IP**；由用户按账号数量自行管理调优 |
| 同时持有 IP 数上限 | `GEO_DPS_MAX_IPS` | 5（= 平台数） | 正常不该触发：浏览器数 ≤ 平台数。触发即说明配额/清理逻辑有问题 |
| 复用阈值 | `GEO_DPS_MIN_TTL_SEC` | 60 | 剩余有效期 ≤ 此值的 IP 不再使用（**按到期处理**：解散，再先并入未满 IP、都没有才取新），避免任务跑到一半 IP 就没了 |

**扩散度算术**（务必心里有数）：`需要的 IP 数 = ceil(每个平台的活跃账号数 / N)`。

| 每平台活跃账号数 | N=2 | N=1 |
|---|---|---|
| 2 | 1 枚（5 个浏览器必同 IP） | 2 枚 |
| 3 | 2 枚 | 3 枚 |
| 5 | 3 枚 | 5 枚（才够真正分散） |

即：**新池子里每平台第一个账号一定都落在同一枚 IP 上**；只有某平台账号数超过 N 才会冒出下一枚。
想看到「5 个浏览器分散在 5 个 IP」需要 N=1 且每平台 ≥5 个活跃账号。

## 2. 判定流程（每次「取账号 → 取 IP」时执行，串行）

```
acquireIpForAccount(platform, account)
  ├ 先取该账号的现有绑定 held（无论是否已到期都要先取，否则判不出「到期 → 另取新 IP」）
  ├ 清理池内已到期的 IP（连同它们的全部账号绑定）        ← 到期即解散
  ├ held 存在？
  │   ├ 剩余 > minTtl  → 复用（同一账号在有效期内固定走同一出口，出口 IP 不频繁跳变）
  │   └ 已到期/剩余不足 → **删掉该 IP 及其全部绑定**                            （用户规则 2.1）
  │       ├ 池中还有「未到期 && 本平台绑定数 < N」的 IP → **并入**（省 IP，不因一枚到期就再取一枚）
  │       └ 都没有 → 取新 IP 并绑定当前账号
  └ held 不存在？（用户规则 2.2）
      ├ 找「未到期 && 本平台绑定数 < N」的 IP：绑定数升序 → 剩余时间降序 → 并入
      └ 找不到 → 取新 IP 并绑定（受 GEO_DPS_MAX_IPS 约束）
```

要点：**IP 到期不做整体迁移，直接解散**；账号下次取用时**优先并入其他未满的有效 IP**（省 IP），
只有池中确实没有富余时才取新 IP →「IP ↔ 账号」组合自然打乱。
打乱频率：账号冷却 120–300s（中位 ~210s）、IP 窗口 1800s → 同一账号约每 8 轮换一次出口 IP。

> 为什么「解散后要先找未满 IP」而不是直接取新（2026-10-16 用户追加口径）：
> 一枚 IP 到期时，它的账号只是失去归属、并不需要新 IP——池中往往还有别的未满 IP 可以接。
> 直接取新会让持有 IP 数随每次到期单调增长，很快撞到 `GEO_DPS_MAX_IPS`。

## 3. 串行与并发约束（用户 2026-10-16 定）

| 环节 | 实现 |
|---|---|
| 取账号 + 取 IP + 绑定 | 允许串行而非事务：`allocateAccount` → `acquireIpForAccount` 顺序调用；绑定侧由**模块内单队列**串行（`bindQueue`），故不存在并发写文件 |
| 取 IP | 必须串行：`getdps` 一次一枚（`num=1`）+ 在途 `refillPromise` 去重 |
| 拉起浏览器 | 串行（`launchSerialized`）：一个拉起完成后再拉起下一个；排队等待上限 60s（单个卡死不拖住全局） |
| 同时浏览器数 | 上限 = 平台数，**一个平台只开一个**（调度器 `MAX_PER_PLATFORM=1` + 槽位 = 启用平台数） |

## 4. 持久化（`<数据根>/dps-pool.json`）

```jsonc
{
  "savedAt": 176xxxxxxx,
  "ips": [
    {
      "server": "http://122.246.13.212:12305",
      "expiresAt": 1792122081969,               // 绝对到期时刻（取 IP 时查一次 getdpsvalidtime 换算）
      "bindings": { "qwen": ["qwen-12"], "doubao": ["doubao-20", "doubao-21"] }
    }
  ]
}
```

- 只存 `server / expiresAt / bindings`，**账密不落盘**（读取时由配置注入）。
- 旧格式 `{proxies:[{server,validAt,checkedAt}]}` 启动时自动换算迁移（`expiresAt = checkedAt + validAt*1000`），无绑定的旧 IP 视为空闲。

## 6. 验证（2026-10-16，真实快代理 + 真实账号）

| # | 场景 | 结果 |
|---|---|---|
| ① | 新账号取 IP | `新建并绑定：qwen/qwen-12 → http://58.19.54.156:12547（有效期 1800s，本平台 1/2）` |
| ② | 同平台第二个账号 | `绑定并入：qwen/qwen-13 → 同一 IP（剩余 1794s，本平台 2/2）` |
| ③ | 同平台第三个账号（N=2 已满 + 上限=1） | `⚠️ 持有 IP 数已达上限 1 → 不再取新 IP`（返回 null，调用方回退） |
| ④ | 原账号再次取用 | `复用绑定：qwen/qwen-12 → 同一 IP` |
| ⑤ | 绑定 IP 仅剩 8s（按到期处理） | `解散该 IP 及其全部绑定 → 新建并绑定（旧 IP 与 qwen-13 的绑定同时消失）` |
| ⑥ | 换平台账号 | `绑定并入：doubao/doubao-20 → 同一 IP（本平台 1/2）` —— 跨平台共用同一 IP ✓ |
| ⑦ | 上限恢复 5 | `doubao/doubao-21 并入（本平台 2/2）` |
| ⑧ | 绑定 IP 到期 + 池中另有未满 IP（N=2，**同进程**） | `解散该 IP 及其全部绑定` → `绑定转移（原 IP 已解散）：qwen/qwen-12 → http://10.0.0.2:1002（本平台 2/2）`——**全程无 getdps 调用**（没浪费一枚新 IP） |
| ⑨ | 绑定 IP 到期 + 池中无未满 IP（N=1，**同进程**） | `解散…` → 池中无可并入 → `新建并绑定：qwen/qwen-12 → 115.231.184.89:11146` |
| — | 旧格式迁移 | 启动日志 `恢复 1 枚 IP（清理已到期 1 枚）` ✓ |

**⑤ 暴露并修掉一个真 bug**：首版只打了「解散」日志却没真删，该 IP 仍占着上限名额 → 新 IP 取不回来。
修法：解散分支显式 `ips.filter(server !== held.server)` 后再取新 IP。

**⑧⑨ 为什么必须「同进程」验证**：CLI 每次运行都在启动时 `loadPool()`，已到期的 IP 会在 `findHeld` 之前被清掉，
于是「到期 → 解散 → 转移」永远走不到（退化成「无绑定」分支，功能结果相同但路径不同）。
生产环境是常驻进程、IP 在运行中到期，故验证脚本用「短 TTL（2.5s）+ 进程内 sleep」把这条路径复现出来。

## 7. 尚未做 / 待定

- **失败重试不换 IP**：出口由绑定决定，同账号重试仍走同一枚 IP（原 `fetchDpsProxy(retried)` 的 forceFresh 已移除）。
  若某 IP 真不可用，只能等它自然到期（≤30 分钟）后随解散换新——用户未定义「换 IP」流程，故不擅自加。
- **到期后先并入其他未满 IP**（2026-10-16 用户追加口径，已实现）：绑定 IP 到期 → 解散该 IP 及其全部绑定 →
  先找「未到期 && 本平台 <N」的 IP 并入；都没有才取新 IP。避免持有 IP 数随每次到期单调增长。
- ~~单 IP 并发上限 M~~：用户已明确**不设**（浏览器数上限恒为平台数）。
- 单 IP 只承载「同平台账号数」配额，未按带宽设并发闸门。
