# 回答结束判定改造：发送控件状态（getSendState）

> 2026-10-12 ｜ 涉及：src/types.ts + 5 个平台适配器 ｜ tsc 通过，DeepSeek 已端到端验证

## 1. 背景与问题

各平台 `waitForAnswer` 依赖「回答完成」信号判定流式输出结束。现状分三档：

| 信号强度 | 平台 | 依赖 |
|---|---|---|
| 强 | qwen | 官方完成 class `qk-markdown-complete` |
| 中 | doubao / wenxiaoyan | 语义稳定的动作栏按钮（aria-label / cos-icon） |
| 弱 | hunyuan / deepseek | CSS Modules 哈希类（`Repeat_`、`db183363`） |

弱点：**哈希类随前端构建变化即静默失效**，只能回落文本稳定兜底；DeepSeek 甚至完全没有元素级完成信号，风控静默挂死时表现为「空答案照常完成」，无任何诊断信息。

## 2. 改动思路

用户提议：发送前按钮可点击、生成中不可点击，用发送按钮状态判生成结束。

实测修正了这一表述（定标数据见 `analysis/sendstate/REPORT.md`）：

1. **生成中不是「禁用」而是「图标替换」**——发送图标被换成停止/中断图标，多数平台仍可点击（用于中断生成）；
2. **`disabled`/`aria-disabled` 与生成状态无关**——它们只反映输入框是否为空（空输入与完成后输入已清空时都会禁用）；
3. 因此信号定义为 **send 态 / generating 态二分**，锚点用图标形状、aria-label、data-testid 等语义特征，不用哈希类。

由此新增统一钩子 `getSendState()`（可选接口，各平台私有实现），并按平台现状差异化接入，**不替换**已有强信号判定（第二轮迭代后升级为五平台统一的「生成态闸门」，见 §4）。

## 3. 五平台定标锚点（2026-10-12 实测）

| 平台 | 生成中（generating） | 待发送/完成（send） |
|---|---|---|
| deepseek | 发送图标 svg path 切为停止图标 | path 回发送图标（与发送前基线比对，无 aria 状态位） |
| doubao | 发送钮被中断钮替换：`[data-testid="chat_input_local_break_button"]` 在场 | 中断钮消失、发送钮回归 |
| qwen | `button[aria-label="停止回答"]` | `aria-label="发送消息"` |
| hunyuan | `#yuanbao-send-btn` aria-label=「停止回答」 | aria-label=「发送」 |
| wenxiaoyan | `span.ci-submit-button` 内 `img.ci-submit-pause` | 内含 `img[src*="send-icon"]` |

注意：wenxiaoyan 的发送控件是 `span`（非 button/role=button）；豆包 aria-busy 实测全程 false，不可单独依赖。

## 4. 接入方式：统一「生成态闸门」（2026-10-12 第二轮，五平台一致）

用户补充关键场景：**思考/检索阶段文本零增长，但生成并未结束**——纯靠「文本无增长」判定会在这时误判完成、抽到半截或空答案。而发送控件状态是唯一能区分「思考中（generating）」和「真完成（send）」的信号。

因此五平台统一为同一套判定结构：

```
每轮采样：sendState = getSendState() + 文本长度

⓪ 平台明确完成标志（qwen 官方 class / 各家动作栏基线计数）→ 立即完成（保留）
① sendState === 'generating' → 一律不判完成（思考中，文本不增长也继续等）
② 纯文本兜底（流式结束+稳定 / 从未增长 Ns 等）→ 仅 sendState !== 'generating' 时允许触发
硬上限 timeoutMs 防失控；结束时仍 generating → 打「疑似挂死/风控」日志
```

各平台被闸门保护的兜底路径：

| 平台 | 受闸门保护的兜底 | 明确完成标志（不受闸门影响） |
|---|---|---|
| deepseek | 从未增长 45s | 动作行基线计数 + 文本稳定 3s；另保留 ⓪′「见过 generating → 回 send + 稳定 5s」 |
| doubao | 流式后 5s 稳定；从未流式 30s | 动作栏（朗读/更多 aria-label）基线计数 |
| qwen | everGrew 后 8s 稳定；从未增长 40s | 官方 class `qk-markdown-complete`，**出现即收尾**（2026-10-16：去掉额外 2s 文本稳定） |
| hunyuan | everGrew 后 8s 稳定；从未增长 40s | 动作栏（Repeat_/ToolbarSuitable_）基线计数竞速（2026-10-12 实测补基线：残留动作栏曾致 0.04s 假完成） |
| wenxiaoyan | 6s 稳定；20s 强制；从未增长 30s | 动作栏（cos-icon-copy）基线计数 |

降级语义：`getSendState()` 返回 `unknown`（锚点失效/未找到）时不参与闸门，保持原判定行为——**平台改版只会退化为旧行为，不会死等也不会误判**。

挂死日志价值：区分「还在生成」与「流已死但没答案」，风控/服务异常时本轮结果可标记可疑，而非静默空答案。

## 5. 设计边界与已知限制

- **秒回竞态**：生成短于一个轮询周期会错过 generating 态 → 状态机只作停止条件，文本增长基线兜底保留；
- **哈希遗留**：deepseek 基线比对、doubao 中断钮 testid 均为语义级；hunyuan/qwen/wenxiaoyan 现有动作栏信号中的哈希类（`Repeat_` 等）未动，失效时由现有兜底承接；
- **锚点漂移**：平台改版可能更换图标/aria 文案，失效表现为 `getSendState` 恒为 `unknown`（自然退化为原判定），不会误判。

## 6. 验证

- `npx tsc --noEmit` 通过；
- DeepSeek 真实浏览器端到端（`analysis/sendstate/verify-deepseek.mts`）：`getSendState` 现场序列 `generating → send`，`waitForAnswer` 11.2s 完成，答案 1057 字；
- 其余四平台锚点来自定标轮实测（`analysis/sendstate/calibrate.mjs` 可复跑）。

- `src/types.ts`：`SendState` 类型 + `PlatformAdapter.getSendState?()` 可选钩子

## 8. 元宝（hunyuan）挂代理发送失败与页面恢复（2026-10-15）

### 现象
- 挂动态代理启动浏览器时，元宝有时首屏即登录页，需刷新才能进会话页。
- 输入问题点发送后偶发 `request abort`：问题气泡留在会话里但 AI 永不回答，发送钮一直停在「停止回答」。

### 实测结论（探针 + 落盘 DOM）
- abort 轮的 DOM：`.agent-chat__bubble--ai` 是**空壳**（内部只有空的 `.agent-chat__speech-text--box`），
  用户条 `data-conv-outputting="true"`、AI 条 `--hidden` → 请求未被服务端受理。
- **两个假阳性信号**（都只代表前端 UI 进入生成态，不代表服务端在生成）：
  1. 「AI 气泡元素存在」——abort 时元宝也会立刻创建空气泡；
  2. 「发送钮 aria-label=停止回答」——abort 后按钮同样停在停止态。
- 旧逻辑同时踩了这两个坑：把 abort 判成「发送成功」→ 不刷新重试；又把它当作「生成中」闸门 → 永不满足 → 死等 180s 硬上限、抽到空答案。
- 过程监控读不到正文：`.agent-chat__bubble--ai` 的 textContent 长期为空（正文经 speech 层/GPU 加速渲染）→ 进度日志恒为「容器 0 字」。

### 修复
| 项 | 做法 |
|---|---|
| 页面恢复 `recoverPage()` | 就绪判据用**会话页特征**（`#yuanbao-send-btn` / `.agent-chat__input-box` 可见），**不用 textarea**（登录页同样有 textarea → 会把登录页误判为正常页、永不刷新）；**登录页或任何异常页一律刷新**（URL `login/passport/sso/error`，或「扫码登录/页面不存在/网页无法访问/加载失败」等文案）；会话特征在场则不刷新 → **刷新 ≤5 轮** |
| 发送就绪门 | 门1 等发送钮出现（上限 20s，快速失败交外层刷新）；门2 等发送钮由禁用转可用（`disabled` / `aria-disabled` / `SendButton_disabled`） |
| 发送确认 `confirmSent()` | **唯一判据 `[data-conv-speaker="ai"][data-conv-outputting="true"]`**（官方状态属性，比哈希类稳定） |
| 失败重试 | `sendQuestion` = 「限时尝试 + 刷新重来」≤3 轮；单轮确认窗 30s（点击）/ 15s（Enter 兜底） |
| 过程监控 | 多候选取「文本最长」（追加 `[data-conv-speaker="ai"]`、`.hyc-common-markdown`、`.hyc-content-md`）；兜底闸门加 `!outputting` |
| 挂死识别 | 按钮停在生成态但 AI 无输出连续 45s → 判 request abort/挂死，提前结束本轮（不再死等硬上限） |

### 验证（真实代理 + 真实账号）
```
recoverPage 18s（未进登录页）
→ sendQuestion 18s：sendState=generating + aiOutputting=true（真确认）
→ waitForAnswer：📝 回答流式输出中…（容器 976 字）   ← 修复前恒为「容器 0 字」
→ 15.3s 命中 action-bar → getAnswer 1460 字（内容正常）
```
总耗时 67s。abort 场景的刷新重试与 45s 挂死提前退出待自然复现验证。

## 9. 豆包（doubao）发送时机与「已提交却被刷新」（2026-10-16）

### 现象（用户反馈）
- 发送提问时仍偶发「系统异常」，问题发不出去。
- 有时问题**已经发出去了**、正在准备回答时，脚本又把页面刷新掉。

### 现场（日志 `geo-browser-data/logs/geo-browser.log`，账号 doubao-20，代理 58.19.55.15）
```
09:23:27 打开页面即为降级页（该页面暂时不可用）→ 自动刷新恢复（第 1/3 次）
09:24:23 ✅ 输入区就绪 → ⏳ 会话区晚期标记未出现
09:25:13 ⚠️ 会话区晚期标记 60s 未出现（按已就绪继续）        ← 日志谎报：实际只等 ~50s
09:25:28 ✅ 发送钮已就绪（等待 11s）
09:25:47 ⚠️ 提交被拒（系统异常，文字仍在框）               ← 第 1 轮
09:26:04 ⚠️ 上一轮 100s 内未确认发送 → 刷新页面重试（第 1/3 次）
09:27:28 ✅ 会话区完整挂载（等待 30s）
09:27:49 ⚠️ 提交被拒（系统异常，文字仍在框）               ← 第 2 轮
09:28:38 ⚠️ 上一轮 100s 内未确认发送 → 刷新页面重试（第 2/3 次）
09:29:34 ✅ 会话区完整挂载（等待 36s）→ 09:30:32 [10.3s] 回答流式输出中…（1511 字）  ← 第 3 轮成功
```

### 定位到四个缺陷
| # | 缺陷 | 后果 |
|---|---|---|
| 1 | 「系统异常」按**页面上是否存在**判定 | 同一会话残留的旧提示让**已提交**的提问被判为被拒 → 立即刷新，**刷掉正在准备的回答** |
| 2 | 提交确认窗口用 `rem()`（本轮 100s 预算的余额） | 前置「挂载等待 + 按钮门 + 逐字打字」把预算吃掉大半——实测点击发送时**只剩 16s**，回答 20s 未开始即判失败 → 触发刷新 |
| 3 | 打字前不检查输入框是否已非空 | 豆包把未发送文本作为**草稿**持久化，reload 后回填 → 再打字等于「追加」，DOM 有文本而应用状态是旧文本 → 提交被拒 + 文字留在框里（连续失败） |
| 4 | 刷新前不自检生成态 | 已进入生成仍执行 reload |

### 修复
| 项 | 做法 |
|---|---|
| 系统异常判定 | 采集**发送前可见数基线**，只有 `当前可见数 > 基线`（本轮新增）才算被拒；存量提示打 `ℹ️` 日志不计成败 |
| **阶段预算独立化**（用户定，2026-10-16） | 输入区就绪门、会话区挂载等待、发送钮就绪门、**提交确认窗**各自拿满 `navTimeoutMs`(100s)，互不侵蚀（原实现共用一个 `attemptSend` 入口 deadline）；提交确认窗从点击时刻起算 100s；重试循环的「预算耗尽即退出」加前提「文字仍在框」 |
| 输入框前置清空 | 打字前断言空框，非空先 `Ctrl+A` + `Delete`（兜底 `Backspace`）再输入；清空结果落日志（`🧹`） |
| 刷新前自检（两道） | ① `isGenerating()`（中断钮 / 加载胶囊可见 / `aria-busy`）为真；② **输入框已不含本轮问题**（豆包只在被拒时才回填文字，故此判据覆盖「已受理但回答未开始」的窗口）→ 任一成立即**放弃刷新**，交由回答等待阶段 |
| 挂载等待预算 | 由硬编码 60s 改为独立 `navTimeoutMs`（原写法每轮用 `rem()` 重算 → 上限随余额缩水且日志谎报 60s） |

### 待验证与并存因素
- 修复后的行为待下一轮日志确认：`ℹ️ 发送前页面已有 N 个可见「系统异常」提示`、`🧹 输入框清空结果`、`🚫 刷新前自检：页面已在生成`。
- **并存的服务端因素**：本轮同 IP（58.19.55.15）同时承载 5 个平台（DPS 池当时仅 1 枚可用 IP），且首屏即降级页——「系统异常」本身也是账号/IP 被限流的症状（此前 doubao-21 同理），非纯时序问题。

## 10. 千问（qwen）回答结束识别延迟（2026-10-16）

### 现象（用户反馈）
「问题回答结束后，没有很快识别出结束标识，而是等一段时间才发现结束了。」

### 现场（`geo-browser-data/logs/geo-browser.log`，账号 qwen-1 / qwen-2 / qwen-13 …）
每一轮都是同一副样子——`🏁` 自己的计时只有 2s，却发生在验证检查之后 17s：

```
09:43:13 🔓 未检测到滑动验证弹窗
09:43:30 [2.0s] 🏁 回答完成标志 qk-markdown-complete 出现且文本稳定，当前 1589 字
09:44:35 🔓 未检测到滑动验证弹窗
09:44:52 [2.0s] 🏁 …当前 1528 字
09:45:55 🔓 未检测到滑动验证弹窗
09:46:12 [2.1s] 🏁 …当前 22735 字
```

`[2.0s]` 是 `waitForAnswer` 内部计时：说明它一开始跑，答案**早已输出完毕**（文本稳定且官方完成类在场）。
差额落在 `captcha 结束 → waitForAnswer 开始` 之间，**恒为 15s**。

### 定位
| # | 缺陷 | 后果 |
|---|---|---|
| 1 | `run.ts` 的「03 截图前等回答开始渲染」循环（15×1s）与 `dbg` 无关地执行，且判据写死了**文心专属类** `.chat-search-answer-generate, .answer-box` + `[class*="capsule-loading"]` | 千问永不命中 → 每轮白等满 15s。该循环的唯一作用是给**仅调试模式**才落盘的 `03-answering.png` 选时机，生产模式（`artifactMode=none`）纯粹是空耗 |
| 2 | `isComplete()` 用 `document.querySelector('[class*="qk-markdown"]')` 取**文档序第一个** markdown 根 | 多轮会话里那是最旧一轮，本轮的完成标志读不到（当前每轮都是新会话，故未暴露） |
| 3 | 完成判定要求 `complete && noGrowth >= 2` | 官方 class 本就是权威「输出完毕」信号，还要白等 ~2s |

### 修复
| 项 | 做法 |
|---|---|
| 15s 空等 | 该循环移入 `if (dbg)`（其作用只是 03 截图时机）；判据改用**平台声明的** `def.selectors.answerContainer`，不再写死文心类（遵守「平台操作私有」原则） |
| 完成标志范围 | `isComplete()` 改读**最新一轮** `chat-round` 内部（无该锚点时退回整个文档，保持旧行为）；正文长度 `getAnswerLen()` 同样按最新一轮读 |
| 完成判据 | 改「**完成标志数 > 提交前基线**」判本轮完成（`sendQuestion` 开头、按 Enter 之前采集基线）。增量判定既排除上一轮残留标志的假阳性，也不受「答案在 waitForAnswer 开始前就已输出完」（验证码耗时期间）影响 |
| 等待时长 | `noGrowth >= 2` → `>= 1`：官方 class 出现后最多再确认一个轮询周期；`noGrowth>=1` 只用于防「同一轮内分块渐进完成」（前一块先带 complete、正文仍在流式）被误判为整轮结束 |

### 验证（真实代理 + 台账账号，本轮改动后）
```
09:51:10 🛡️ 未发现营销弹层
09:51:45 🔓 未检测到滑动验证弹窗
09:51:46 [1.1s] 🏁 回答完成标志 qk-markdown-complete 出现，当前 2061 字   ← captcha → 🏁 由 17s 降到 1s
09:51:48 ✂️ Q&A 长屏截图完成（328988 bytes）→ 抽到 15 条信源
```
总时长 65s（含 35s 验证检查窗口；答案即在该窗口内输出完毕，基线增量判定正确识别为本轮完成）。

## 11. 豆包（doubao）提交仍被拒 + 「异常后不再处理提交」（2026-10-16 第二轮）

### 现象（用户反馈）
1. 提交时仍出现「系统异常」。
2. 出现「系统异常」后脚本**不再处理提交**，几次都要人工手动再点发送。
3. 兜底诉求：文字输入完成、检测到可提交后，**再等 5s** 才提交。

### 现场（日志，账号 doubao-20 / 代理 58.19.54.152）
```
10:36:51 ✅ 会话区完整挂载（等待 34s）
10:37:11 ⚠️ 提交被拒（本轮新增「系统异常」，文字仍在框）→ 第 1 次间隔重试
10:37:17 ⚠️ 重试前复核未就绪（按钮禁用/区未挂载），跳过本次补发      ← 一次提交都没发起
10:37:17 ⚠️ Enter 未被确认（文字仍在框）→ 第 2 次兜底重试
10:37:23 ⚠️ 重试前复核未就绪（按钮禁用/区未挂载），跳过本次补发      ← 又是一次都没发起
10:37:23 ⚠️ Enter 未被确认（文字仍在框）→ 第 3 次兜底重试
```
三次重试**全部被跳过、零动作**——这正是用户说的「出现系统异常后就不再处理提交」。

### 三个缺陷
| # | 缺陷 | 后果 |
|---|---|---|
| 1 | 重试前「复核未就绪」时 `continue` 跳过本次重试 | 就绪复核连续不通过 → 3 次重试**一次提交都没发起**，用户只能人工补发 |
| 2 | `clickSend()` 在按钮不可用/元素缺失时**静默 return**，无任何日志 | 「没发起提交」在日志里不可观测 |
| 3 | 「系统异常」基线只在发送前取一次 | 首次被拒后气泡若仍在场，之后每次确认都立刻判「本轮新增」→ 把**其实已提交**的重试判失败 → 放弃/刷新 |
| 4 | 打字完成到提交之间没有稳定等待（仅 0.5~1.0s 拟人停顿） | 豆包前端把文本同步进应用状态有延迟，过早提交送出「空/旧内容」被服务端拒收 |

### 修复
| 项 | 做法 |
|---|---|
| 提交前稳定等待 | 新增 `DOUBAO_INPUT_SETTLE_BEFORE_SEND = [5000, 0]`（固定 5s，等应用吃进文本，非拟人停顿）；每次提交动作（含重试）前都执行，日志 `⏳ …：提交前稳定等待 5s` |
| 重试不再空转 | 去掉「复核未就绪 → continue 跳过」；改为 `waitSendReady(15s)` **等就绪后再提交**；超时也仍尝试点击（点击内部再校验一次） |
| 点击留痕 | `clickSend()` 返回是否真发出点击，并打 `🖱️ 已点击发送钮` / `⚠️ 发送钮当前不可用 → 本次未点击` |
| 统一用点击 | 重试也改用点击（原 `retry===1` 用 Enter——实测 Enter 常为死键/触发回填） |
| 异常基线可变 | 新增 `rebaselineErrors(label)`：**每次提交动作前重置基线**，「本轮新增」始终针对最近一次提交（日志 `ℹ️ 第 N 次重试：重置「系统异常」基线 1 → 2`） |

### 一次被实测证伪的捷径（重要教训）
第一版还加了「快窗 15s 无信号 + 文字仍在框 → 判未提交、立即重试」。实跑（11:30 轮）当场证伪：
```
11:30:10 🖱️ 已点击发送钮
11:30:26 ⚠️ 提交未被确认（文字仍在框，明确未提交）→ 第 1 次重试   ← 据输入框状态判「没提交」
11:30:48 ℹ️ 第 1 次重试：输入框已不含本轮问题（可能已提交）→ 不再点击
11:31:02 [10.4s] 📝 回答流式输出中…（容器 928 字）
```
那次点击**其实已被受理**（框 22s 后才清空、42s 后才出答案），只是豆包把文字留在输入框里超过 16s。
→ **「用输入框状态反推没提交」在这条链路上不成立，已撤回该捷径**，恢复整窗等待；判「被拒」只认正面证据
（本轮新增「系统异常」气泡 / 降级页）。

### 验证（真实代理 + 台账账号，撤回捷径后的干净路径）
```
11:33:45 ✅ 会话区完整挂载（等待 40s）
11:33:56 ⏳ 首次提交：提交前稳定等待 5s（等应用吃进文本）
11:34:02 🖱️ 已点击发送钮              ← 单次点击，无「系统异常」、无重试
11:34:38 [10.2s] 📝 回答流式输出中…（容器 367 字）
11:35:10 [42.1s] 🏁 检测到回答动作栏 → 2367 字 → ✅ 完成
```
两轮实测（11:28 / 11:32）均**未再出现「系统异常」**，提交一次成功，总时长约 2.7min（含 40s 挂载等待）。

### 并存因素（非时序问题）
- 本轮同 IP 同时承载多平台多账号（DPS 套餐 `num=1`，池内常只有 1 枚 IP），「系统异常」本身也可能是账号/IP 被限流的症状。
- 5s 稳定等待与重试修复能消除**误判与空转**，但治不了真实限流。

## 12. 慢网络下「系统异常」是假阳性 + 重试补发的重复提交风险（2026-10-16 第三轮，**仅记录，未改代码**）

### 现象（用户反馈）
1. 点击提交后，请求约 **16s 后**才真正发出。
2. 开启代理后，豆包页面比直连慢很多。

### 现场（回看第 11 节同一轮日志，HEAD 版代码）
```
10:36:18 ✅ 输入区就绪（发送钮已渲染）
10:36:51 ✅ 会话区完整挂载（等待 34s）
10:37:11 ⚠️ 提交被拒（本轮新增「系统异常」，文字仍在框）→ 第 1 次间隔重试   ← 挂载后 20s
10:37:17 ⚠️ 重试前复核未就绪 → 跳过本次补发（continue，零补发）
10:37:17 ⚠️ Enter 未被确认（文字仍在框）→ 第 2 次兜底重试                  ← 此处 submitErrorSeen 已为 false（气泡自消）
10:37:23 ⚠️ 重试前复核未就绪 → 跳过本次补发（continue，零补发）
10:37:43 [10.7s] 📝 回答流式输出中…
```
同一时间线在 10:34 轮重复出现（`10:34:11 挂载 → 10:34:29 判被拒`，间隔 18s），量级与用户观察的 16s 一致。

### 推论（本轮重点）
旧代码两次重试都走 `if (!canSend) { …跳过本次补发; continue; }`（HEAD 版 `DoubaoAdapter.ts:663`），**一次提交动作都没发起**，而回答照常流出
→ **10:37:11 那次「被拒」是假阳性：请求其实已被服务端受理**，只是代理链路慢/超时，前端先弹了「系统异常」并把文字回填输入框。

由此得到两条硬结论：
1. **「本轮新增系统异常 + 文字仍在框」在慢网络下不足以断定「未提交」**——它与第 11 节被证伪的「输入框状态反推」属同类谬误，只是证据形态不同。
2. **第 11 节的「重试不再空转」修掉了空转，同时移除了旧代码那个（意外的）防重复护栏**：
   现在的重试路径会在 6s 后**真的补点一次**，而假阳性气泡通常 ~6s 内自消、真正的回答要 20~30s 后才开始
   （10:37 轮：气泡 10:37:11 vs 回答 10:37:43）→ **风险窗口正好落在补发判定里**，一次假阳性即可能变成同会话重复提问/消息排队。

### 时间预算核算（结论：不需要加大超时）
| 预算 | 取值 | 说明 |
|---|---|---|
| `navTimeoutMs`（dev env 实配） | 100s | 会话区挂载、发送钮就绪、提交确认**各自独立**拿满 |
| 会话区挂载实测 | 33~34s | 属打字前预算，不侵蚀确认窗 |
| 提交确认窗 | 打字完成后另起 100s | 16s 网络延迟 + 20~30s 起答完全在余量内 |

→ 5s 稳定等待**保留**（两轮验证都在带它的情况下通过，现有证据不支持撤销；不为此现象过拟合）。

### 待定改进（用户 2026-10-16 决定「先不改代码」，等再实测到假阳性后再定）
| 编号 | 问题 | 拟改法 | 代价 |
|---|---|---|---|
| P1 | 假阳性 → 重试补发重复提交 | 每次补发前加 `isGenerating()` 门：已在生成 → 不补发，回确认 | 极小，纯防呆 |
| P1b | 「本轮新增系统异常」立即判失败过刚 | 改为「标记 + 宽限 20s 观察」：期间出现 answerStarted / 文字清空稳定 → 判成功 | 真被拒时每轮多花 ≤20s |
| P2 | 点击没发出也白等 100s；`click({timeout:5000})` 在卡顿页易动作性超时 | `submitClick` 返回三态（clicked / already-sent / not-clicked），not-clicked 直接短退避重试；`click` 超时 5s→15s | 小，仅豆包发送路径 |
| P3 | 无法量化「点击 → 回答开始」耗时 | 加一行耗时日志（含系统异常出现时刻），用于统计假阳性率 | 仅日志 |

注：P2 的具体落点 —— `submitClick()` 的 bool 返回值目前被丢弃（`DoubaoAdapter.ts:777/805`），「没点成」与「因文字已清空而跳过」两种 false 语义被混同。
